# マイクの同音反復

2026-09-11。従来は80msを超えて音高が検出されないとnoteoffを出さず、検出が一度落ちると音量比較もリセットしたため、短い切れ目の後に同音が戻っても次のnoteonが出ない経路があった。

AudioWorkletで連続した音声を2048サンプルの窓・約25ms間隔で取り出す。解析時刻はオーディオ時計から作り、画面側のタイマーで最新窓だけを読む方式を廃止した。処理が遅れたときも窓を順に処理するが、画面・伴奏への反映が遅延しない保証ではない。音高検出はメインスレッドに残る。録音保存・外部送信は行わず、Worklet出力は無音。停止時はポート・入力接続・コンテキストを解放する。

Workletでは約5msごとのRMSが2窓続けて0.008未満になった切れ目を記録する。音高の検出落ちだけに依存せず、無音を検出した窓では音符を出さず、同じ音高が2フレーム安定して戻るのを待つ。前回onsetから80ms以上を条件にし、noteoff→noteonを送る。音声の切れ目を伴わない1フレームだけの音高検出落ちは再発音にしない。停止時は切れ目・音量・時刻の状態も破棄する。

検証対象:

- 2フレームの短い切れ目、1フレームの検出落ち、停止後の状態初期化。
- A4の基本音＋第3倍音を300ms周期、40ms無音で反復。44.1/48kHzの2048サンプル窓を25msずつ進め、6音のonsetを検出する。検出時刻はこの合成条件で発音から100ms以内。
- Workletの可変長入力ブロックから、連続した窓と正しいオーディオ時刻が出ることを確認。44.1/48kHzそれぞれで開始位相を0/5/10/15/20msずらして同音6回を照合する。
- ChromiumとSwift WKWebViewで実AudioContext→MediaStream→AudioWorklet→音高検出→MicrophoneInput→ConcertEngineを通す。合成音4回で音待ちモードの楽譜が4音分進む。Chromiumではメインスレッドを650ms占有した場合も同じ試験を行う。

最初の全体検証 `verification-results/2026-09-10T18-02-24.008Z` はブラウザ同音反復で失敗。タイマー方式を変更した後も開始位相10/15/20msで音高未検出が1窓だけになる問題を再現した。RMSによる切れ目検出を追加した後、位相別テストとブラウザ6回の反復試験が通過した。失敗記録を成功扱いしない。

これは物理マイク・室内反響・伴奏の回り込み・実際のタンギングを含まない。2フレームの音高検出失敗も切れ目と区別できないため、どんなノイズでも誤発音しない保証ではない。音量が下がらないレガートの同音反復、非常に短いタンギング、高音域の実演精度は別途検証する。合成音での解析遅延はデバイス込みの80ms目標達成を意味しない。
