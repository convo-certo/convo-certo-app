# ACCompanionから次の共奏へ

追加調査: [2026年6〜9月の生成伴奏研究と、持続的な減速への追加改善](2026-09-live-accompaniment-update.md)。以下の長い間に関する制限は、この追加改善前の記録も含む。

## 公開実装の現在地

- [ACCompanion](https://github.com/CPJKU/accompanion): GitHub APIで取得した既定ブランチの最新コミットは2024-01-19、`07e88f1fa34e24f2b5e7aae5a81065b915c199ba`（Extra documentation）。更新停止から研究自体の停止は推定しない。
- [Matchmaker](https://github.com/pymatchmaker/matchmaker): 既定developブランチの取得時最新コミットは2026-09-03、`40fd6e7602bd9e596cea1beafdcee4853b9f2c98`（Parangonar統合）。ACCompanionと研究者が重なるが、別プロジェクト。
- [0.3.0変更履歴](https://github.com/pymatchmaker/matchmaker/blob/40fd6e7602bd9e596cea1beafdcee4853b9f2c98/CHANGES.md)には、symbolic OLTW、Outer Product HMM、MIDI/audio共通のParticleFilter、BytesAudioStream/BytesMidiStream、MusicXMLテンポ取得などが記載される。これは取得した開発ブランチの記述であり、PyPI配布版や安定APIの保証ではない。READMEと変更履歴のデフォルト方式にも記述差があるため、連携時はコミットを固定し実装を確認する。

[Matchmaker ISMIR 2025論文](https://arxiv.org/abs/2510.10087)は追従方式の共通評価を扱う。ピアノ音声での評価結果を、単音クラリネットMIDIの性能へそのまま転用しない。採用する考え方は、同じ入力を再生して比較し、位置誤差と処理時間を分けて評価すること。実機遅延と演奏者の自然さ評価は別に測る。

[ACCompanion技術付録](https://cpjku.github.io/accompanion_ijcai2023/docs/technical_appendix.pdf)は反応型、移動平均、適応と予測を合わせる方式、Kalmanテンポモデルを説明する。位置の推定・テンポの推定・表情の生成を切り分けて評価する設計の参考になる。

[Streaming Generation for Music Accompaniment (2025)](https://arxiv.org/abs/2510.22105)も確認した。音声から伴奏音声を逐次生成する方向は、将来の自由な即興相手に関係する。ただし、MusicXMLの担当楽器・小節を厳密に指定する今回の用途と同じではない。現段階では組み込んでいない。

## 今回実装したもの

「共奏のチューニング」→「楽譜への追従方式」→「音の並びを追う（実験）」。標準は変更しない。ブラウザとSwiftのWKWebViewで同じTypeScript処理を使い、サーバーへ入力を送らない。

`SequenceFollower`は独自の小さなオンライン探索実装。Matchmaker/ACCompanionの移植・再現実装ではない。

- 同時刻の楽譜音をまとめ、最大8個の位置候補を保持する。
- 各候補から次の8個までの開始位置を探索。音高、前後の時間差、抜けた音の数で候補を評価する。
- 余分な音として入力を見送る候補も保持し、曖昧なときは確信度を下げる。この値は校正された正答確率ではない。
- 標準方式の65ms間隔制限を実験方式には設けない。重複時刻・古い時刻・noteoffは照合しない。
- 方式は席ごとのローカル設定とテイクJSONに含む。同じテイクのA/Bシミュレーションで切り替えられる。演奏中の切り替えはUIで禁止。
- 旧設定には標準方式を補う。練習ファイル `.convo.json` にも追従方式・共奏の調整・合奏の主導者・適用中の表現プロファイルを含め、別端末で復元できる。読み込み時は保存された値が端末の既存設定に優先する。古いファイルも読み込める。

制限: 大きなジャンプ・巻き戻し、装飾音の意味理解、和音入力の完全な照合は未対応。最初の同音反復は音高だけで一意に決まらない。迷ったまま長く吹いたときは楽譜をクリックして位置を指定する。音声入力側のピッチ抽出・onset検出の改善は今回の変更に含まない。ClariMateの物理入力やマイクの精度が合成テストで証明されることはない。

## 比較とチューニング

1. 単音の4〜8小節を選び、ループをOFFにする。同じ入力遅延補正・主導者・テンポを使う。
2. 標準で「テイクを記録して演奏」。録音ではなく音符と応答の記録になる。
3. 終了後、実験方式を選び「同じ入力でA/B比較」。Aは記録時、Bは現在の設定。位置一致回数はシステム自身の判定であり、正解ラベルとの一致率ではない。
4. 両方式で実際に吹き、急ぎ・待ち過ぎ・自然さの感想を別に残す。速いパッセージ、同音反復、1音抜け、余分な音、ritardando、息継ぎを分ける。
5. 次の研究判断には、手で正解位置を付けた実演入力で位置誤差、未照合率、誤照合率、復帰までの音数、入力から応答までのp50/p95を収集する。多数の一致だけで昇格しない。

自動試験は自作の音列を用いる。50ms間隔8音で標準4/8・実験8/8、余分な音と1音抜け、予測のずれた同音反復、曖昧な入り、seekリセット、3600秒分7200音の仮想入力を確認する。1時間の実時間演奏ではない。全体のリリース検証には30秒の実WebAudio処理で120音を鳴らし、席を交換・削除した後の経路と音源の解放も含める。

## 正解ラベル付きの再現評価

`npm run research:benchmark` で、標準・実験方式へ同じ入力を渡し、`verification-results/followers-<日時>/report.json` を生成する。入力音、正解位置、伴奏側の予測位置、各入力の判定を保存する。正解位置を追従器に渡さず、予測位置は120 BPMの独立した時計から作る。伴奏との閉ループ評価ではなく、位置推定部品の評価である。

正解、見逃し、間違った位置への照合、余分な音への誤反応を分離する。位置誤差p50/p95は照合できた正解付き入力のみが対象なので、見逃し件数を必ず併読する。処理時間p50/p95は追従器の計算時間だけで、MIDIデバイス・音声バッファ・OSを含む遅延ではない。空の評価は成功率や遅延を0とせずnullとする。

2026-09-11実行: 自作の単音6条件。定速8/8、同音と予測ずれ8/8、抜け音＋余分な音7/7、徐々に遅くなる8/8は両方式とも一致。50ms音列は標準4/8・実験8/8。予告なしに冒頭へ戻る条件は両方式4/8で、未対応の巻き戻しを再現した。結果から実験方式の全面的な優位や実演精度は主張しない。

追加確認した[Matchmaker demo](https://github.com/pymatchmaker/matchmaker-demo)は、MusicXML等の読み込みとブラウザでの追従表示を提供している。ブラウザ楽譜追従そのものは独自性の根拠にならない。ConvoCertoでは担当パート、伴奏の表情、空間配置と組み合わせた実演体験を評価対象とする。

## Matchmakerの実装を動かした比較

`npm run research:compare` は標準・SequenceFollowerのレポート生成後、`uv run --script scripts/benchmark-matchmaker.py <report.json>` を実行し、同じフォルダーへ `matchmaker.json` と日本語の `comparison.html` を作る。初回はPython 3.12と研究用依存パッケージを取得する。通常のWeb/Swiftアプリの依存・配布物へは追加しない。録音・外部モデル・研究用サンプル曲は評価入力に使わない。MIDIポートやマイクを開かず、入力をサーバーに送信しない。

Matchmakerは `40fd6e7602bd9e596cea1beafdcee4853b9f2c98` に固定し、実際にインストールされたGitコミットも照合する。推移的依存のバージョンはレポートへ記録するが、すべてを固定したlockfileではない。比較元JSONのSHA-256が一致しなければHTMLを生成しない。

[固定したPitchIOIHMM実装](https://github.com/pymatchmaker/matchmaker/blob/40fd6e7602bd9e596cea1beafdcee4853b9f2c98/matchmaker/prob/hmm.py)を直接利用。`piano_range=False`、`has_insertions=False`、KalmanTempoModelをシナリオの開始テンポで生成するfactoryを渡す。入力は単音のMIDI音高配列と秒単位の演奏時刻。正解ラベルと伴奏予測位置をHMMへ渡さない。MIDI特徴抽出・和音の取りまとめ・キュー・発音処理を通したシステム全体の比較ではない。HMMは音ごとに位置を出すので、余分な音への出力は誤反応として数える。初期化時間を処理時間から分離して記録する。

2026-09-11の実行結果（自作の短い単音列）:

|条件|標準|音の並び|Matchmaker HMM|
|---|---:|---:|---:|
|一定テンポ|8/8|8/8|8/8|
|50ms間隔|4/8|8/8|8/8|
|同音反復と予測ずれ|8/8|8/8|8/8|
|音抜けと余分な音|7/7|7/7|7/7、余分な音へ1回出力|
|徐々に遅くする|8/8|8/8|8/8|
|予告なく冒頭へ戻る|4/8|4/8|8/8|
|途中で2.2秒長く息を継ぐ|4/8|7/8|8/8|
|同じ旋律が続く場所で戻る|4/8、誤位置4|4/8、誤位置4|4/8、誤位置4|
|別の場所にある音を間違えて吹く|7/7|7/7|7/7、間違った音へ1回出力|

分子は正解位置、分母は正解ラベル付き入力数。存在しない入力を分母に含めない。速さ・息継ぎ・単純な巻き戻しへの候補としてHMMを評価できる段階になった。ただし、同じ旋律の繰り返しは3方式とも誤る。今の伴奏エンジンは位相補正を±0.6拍に制限しており、推定位置が戻っただけで伴奏全体が自然に戻れるわけでもない。常用方式への自動昇格は行わない。

アダプターの4テストでは実HMMを実行し、正解ラベルと予測値を変えても推定位置が変わらないこと、余分な音の集計、空入力、不正・過大入力の拒否を確認する。実行例: `uv run --python 3.12 --with 'pymatchmaker @ git+https://github.com/pymatchmaker/matchmaker@40fd6e7602bd9e596cea1beafdcee4853b9f2c98' python scripts/test_benchmark_matchmaker.py`。

次に作るべき体験は「迷ったあとに合奏へ戻れる」こと。手で正解位置を付けたClariMateのテイク、反復・息継ぎ・間違いの負例を増やし、復帰候補の提示と奏者の確認、伴奏音を切り替える際の接続を一緒に検証する。単純な位置正解だけを根拠に演奏中の自動巻き戻しは導入しない。

## 長い間の後の入りを改善（2026-09-11、追加実装）

GitHub APIで既定ブランチの先頭を再確認し、ACCompanion `07e88f1`（2024-01-19）、Matchmaker `40fd6e7`（2026-09-03）が上記調査と一致した。公開ソースの更新日であり、研究活動全体の最新日を意味しない。

上の9条件の比較から、SequenceFollowerの遅い入力に対する時間差ペナルティが「余分な音として無視する」候補より大きくなり、長い間の後の正しい最初の音を捨てる問題を修正した。遅い入力の時間差コストを1.4に制限し、早すぎる入力は従来の最大2.1を維持する。音を飛ばすコストは維持する。予想より長い間（0.75秒と現在の1.5拍の大きい方を超過）があった区間はテンポの更新に使わない。以後の音間隔からは通常どおり更新する。

これは音列と時刻に対する独自のヒューリスティックであり、息継ぎの音響検出やMatchmakerの移植ではない。持続的な大幅減速にもこの条件がかかり、テンポを適応できない場合がある。次の正しい音と同じ音高の誤音は区別できず、同一旋律の巻き戻しも未解決。息継ぎ時に伴奏が自動で止まる機能ではない。待ってほしい小節には既存の「小節の入り」→「演奏・うなずき・ボタンの合図を待つ」を使う。

比較結果: `verification-results/followers-2026-09-10T18-32-03.418Z/comparison.html`。長い息継ぎの条件で実験方式は7/8から8/8へ改善した。他の8条件の正解数・誤反応数は従来と同じ。標準方式、実験方式、固定版Matchmaker HMMを同じ入力で実行した。これらは合成単音入力であり、実演の成功率ではない。

追加試験では60/120/180 BPM × 2.2/5/15秒の間、早すぎる遠い音、間が空いた後の無関係な音を確認した。伴奏エンジンの結合試験では、待ち位置より先を発音せず、誤音で解除せず、正しい最初の音で合図待ちを解除して伴奏を発音することを確認した。標準方式は変更していない。WebとSwift内のWebアプリは同じ改善を使う。
