# 伴奏の音質と表現を育てる計画

2026-09-24。現行実装の確認と、次の開発候補。高品質音源の追加、外部音源への接続、SFZエンジンの統合はまだ実装していない。この調査では音源をダウンロードしていない。

軽くする対象は提供する楽譜データであり、音源の品質を下げる要求ではない。持ち込んだMusicXMLで演奏する強みを保ち、音源は必要な楽器だけ高品質にできる構成を検討する。「自分の楽器で合わせたくなる音」と、奏者の息・間への応答を一緒に評価する。

## 現在の音

根拠は [OrchestraAudio](../app/lib/orchestra-audio.ts)、[ConcertEngine](../app/lib/concert-engine.ts)、[MusicXMLパーサー](../app/lib/musicxml-parser.ts)、[音源生成処理](../scripts/prepare_instruments.py)、[出典マニフェスト](../public/audio/fluid/sources.json)。

| 項目 | 実装済みの範囲 | 現在の制約 |
| --- | --- | --- |
| サンプル | FluidR3由来の34楽器。各C1〜C7の7ファイル、計238 MP3。`du -sh public/audio` は約5.8MB | 各音高の発音は1種類。無音サンプルは読み込み時に除外する。これはディスク使用量の概算で、展開後のメモリ量ではない |
| 音高 | 最寄りのCサンプルを再生速度で移調。基準ピッチを変更可能 | 音高と同時にアタックや音色の時間的な特徴も変わる。楽器の実音域に応じた密な録音配置ではない |
| 強弱 | velocity、譜面の強弱曲線、表情指示、入力への応答で音量を変える | 弱く弾いた／吹いた録音と、強く演奏した録音を切り替える層がない。弱音と強音の音色の違いは出せない |
| 奏法 | staccato/staccatissimoは音長、tenutoも音長、accentは強さへ反映 | 奏法別サンプル、実際に音をつないだレガート録音、弦のpizzicato切り替え、連打ごとの別録音は未実装 |
| 長い音 | 管・弦などはサンプル内部をクロスフェードしてループ。譜面の音量曲線を再生 | 息・弓圧による連続的な音色変化はない。現行の表情と入力追従は主に次の発音の強さ・音長へ作用する |
| 発音と消音 | 音量エンベロープを適用 | 基本のアタック8ms、消音120msは楽器共通。実際の離鍵・ダンパー・弓の離れなどの録音はない |
| 合奏と空間 | 奏者ごとの小さな音程・発音時刻・長さ・強さの差、HRTF定位と距離減衰 | 変動は同じ音符・席に対して決定的。ホール残響、初期反射、頭部追跡は未実装。MIDI入力の電子音モニター側のリバーブとは別経路 |
| 再生の負荷 | 最大512ボイス。Web Audioで発音を予約 | 上限では新しい発音を落とす。現在のprepareは曲に使う楽器だけでなく全パレットを準備するため、大容量音源へそのまま置き換えられない |

FluidR3の配布元は、音源をCC BY 3.0として公開している。ソフトウェアのMIT表示と音源の条件を区別する。[MIDI.js Soundfonts公式リポジトリ](https://github.com/gleitz/midi-js-soundfonts)

現在のテイク由来の表現プロファイルは、テンポ・相対強弱・音の長さの曲線である。特定奏者の楽器音色を学習して再現するものではない。奏者モデルの検討は [演奏者モデル計画](performer-model-plan.md) に分ける。

## 改善する順番の提案

1. ピアノと弦の伴奏で、音域と強弱ごとのサンプルを増やす。まず「小さくした同じ音」から「柔らかい音で演奏する」へ進める。ビットレートだけを上げても、この差は解消しない。
2. 奏法と音のつながりを扱う。短い音、長い音、音の終わり、ピアノのペダル、管・弦のフレーズ内の連続強弱を分けて設計する。楽器別のアタックと消音を調整し、自然言語の指示を具体的な発音動作へ対応させる。
3. 控えめな部屋・ホールの残響を加える。直接音と初期反射・残響を調整できるようにし、聴き映えと、練習で入りを聴き取れることを別々に確認する。
4. 奏者モデルの出力を、この表現力のある音源へ接続する。同じモデルでも、その日の奏者のテンポや入りに応答する余地を残す。音色の質と演奏解釈の質を一つの評価に混ぜない。

以上は開発の優先案であり、音源を交換しただけで生演奏と区別できなくなるという保証ではない。

## 高品質音源の候補

容量は配布元の表示であり、ConvoCerto用に再構成した場合の容量は未測定。以下の2候補は未導入で、現在の伴奏は引き続きFluidR3を使う。

| 候補 | 一次資料で確認した内容 | 最初に確かめること |
| --- | --- | --- |
| [VSCO 2 Community Edition](https://versilian-studios.com/vsco-community/) | メーカー公開の約3GBのオーケストラ音源。約3,000サンプル、44.1kHzの16/24bit WAVとSFZ、CC0 | 最初は弦の少数楽器・奏法だけで試す。音域・強弱・奏法の収録範囲は楽器別に確認し、必要な表現が揃うかを評価する。全楽器で実レガートを保証する音源として扱わない |
| [Accurate-Salamander](https://www.ir.isas.jaxa.jp/~cyamauch/AccurateSalamander/index.ni.html) | 開発者公開のピアノ。6.1aは各約1.6GB、48kHz/24bit、16段階のvelocity。CC BY 3.0、楽器への組み込みを歓迎と明記 | まず一つの音色を比較する。レイヤー間の均一性、離鍵、ペダル、発音の遅れを確認する。原作者・改変者・変更内容の表示を保存する |

CC BY 3.0は条件を満たした商用利用・再配布を認める。表示と改変の記録を音源パックへ引き継ぐ。[Creative Commons公式条件](https://creativecommons.org/licenses/by/3.0/)

Accurate-Salamanderの試聴用MP3には再配布禁止の表示がある。音源WAV/SFZの条件と、サイト上の完成した参考演奏の条件は分けて扱う。モデル学習用の演奏録音としても取得していない。

## 必要な楽器だけを追加する配布

初回は現在の標準音源で演奏を始められる状態を保つ。任意の楽譜を開いた後、使用する伴奏楽器に対応した高品質パックを選べる構成を提案する。奏者を追加したときも、その席の楽器だけを準備する。

- パックごとに、楽器、奏法、音域、版、圧縮後の取得容量、保存容量、ライセンス、出典、ハッシュを持つ。
- 取得前に容量を示し、キャンセルと再開に対応する。完了後はオフラインで使えるようにする。
- ディスク上の取得単位と、RAMへ展開する単位を分ける。曲で使用する楽器・音域を先に準備し、全サンプルを一括decodeしない。
- 追加パックがない場合や準備に失敗した場合は、標準音源を使っていることを明示する。練習開始を長時間止めない。
- 練習の保存にはパック名と版を残す。音源そのものを練習ファイルやMusicXMLへ埋め込まない。

これらのダウンロード管理・パック切り替え・キャッシュ管理は未実装。楽譜の収録点数を絞る [スターター配布](starter-bundle.md) とは独立した開発である。

## サンプラー層とSFZ統合

演奏判断と発音を分け、ConcertEngineの出力をサンプラー層に渡す。今の `onNote(note, time, duration, notatedDuration)` を出発点とし、奏法、音色内の強弱層、連続コントロール、発音後の更新・消音をどう扱うかを定義する。ロード・ストリーミング・モデル推論を、発音スケジューラの同期処理へ入れない。

Web版には、採用するSFZの必要な範囲を事前にマニフェストへ変換し、現行Web Audioサンプラーを拡張する案がある。レイヤー選択、クロスフェード、ループ、release、奏法ごとの選択を明示する。SFZファイルを読めることと、必要なopcodeを再現できることは別に検証する。汎用SFZ完全互換や、任意のVSTをブラウザでそのまま使えることは約束しない。

Mac版はC/C++のSFZエンジンを組み込む案も比較対象にする。[sfizzの公式説明](https://sfz.tools/sfizz/)はオンデマンドのストリーミングとSFZv1・SFZv2部分対応を示している。ただし [sfztools/sfizz公式リポジトリ](https://github.com/sfztools/sfizz) は2026-06-21にアーカイブされている。採用時は保守先、固定する版、依存ライセンス、対象SFZの互換性を先に確認する。ライブラリ本体のBSD-2-Clause表示だけで、依存物やプラグイン全体の条件を代用しない。

Salamander系のSFZにはARIA拡張を使う機能があるため、ペダルやreleaseの実動作を比較する。現在のMacアプリはこのサンプラーを搭載していない。外部MIDI音源、Audio Unit、VSTの接続も未実装で、ユーザーが所有する音源を利用する将来案として扱う。

## 小さな品質評価から始める

最初はピアノ1種類と弦1種類、各4〜8小節の短い試聴だけを対象にする。少数の音域・必要な強弱層を使った試作で、サンプラーと評価手順を確認してから対象を広げる。ここでの少量化は試験範囲であり、製品音源の品質を落とす方針ではない。

1. 弱音と強音、同じ音の連打、長い音、短い音、つながるフレーズを含む同一MusicXMLを用意する。権利を確認した譜面か自作の短い課題を使う。
2. 現行音源と候補音源で、演奏イベント・テンポ・区間・定位を固定する。最初は残響なし、音量差を揃えて比べる。次に同じ残響条件でも聴く。
3. 少人数の奏者に、音色の自然さ、強弱・奏法の聴き分け、伴奏に合わせやすいかを別々に評価してもらう。順序と音源名を伏せ、実際に楽器で合わせる試験も行う。購入意向や一般化を、小さな試験だけで断定しない。
4. 音割れ、ループの継ぎ目、急なレイヤー切り替え、連打の不自然さ、持続音の消失を調べる。開始・停止・待機・途中再開・出力先切り替えも確認する。
5. 初回準備時間、再試聴までの時間、ピークメモリ、CPU、ドロップアウト、発音の実測遅延を記録する。新音源で良く聴こえても、追従や入りの失敗が増える場合は採用を保留する。

継続の基準は、同じ指示の音の差が伝わり、現行音源より合わせたくなると評価され、発音と追従の安定性を損なわないこと。現在の自動テストはこの聴感評価を代替しない。品質pilot、配布パックの作成、SFZ統合はいずれも今後の作業である。
